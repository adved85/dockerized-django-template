# Bootstrap Guide — build this project from an empty folder

The only files you ever create by hand are the infrastructure files below.
Everything under `app/` (manage.py, config/, the whole Django project) is
generated by commands, run through temporary containers. You never install
Python on the host and you never `mkdir`/create app files yourself.

## 1. The template (hand-written files)

Create exactly this, nothing else:

```
project/
├── docker/
│   ├── django/
│   │   ├── Dockerfile.dev
│   │   ├── Dockerfile.prod
│   │   └── settings.overwrite.py
│   ├── nginx/
│   │   ├── Dockerfile.prod
│   │   └── nginx.conf
│   └── caddy/                  (alternative to nginx, see Step 6)
│       ├── Dockerfile.prod
│       └── Caddyfile
├── requirements/
│   ├── base.txt
│   ├── dev.txt
│   └── prod.txt
├── .env.dev
├── .env.prod
├── docker-compose.dev.yml
└── docker-compose.prod.yml
```

That's it — 14 files, no `app/` directory yet. Contents:

- `requirements/base.txt` / `dev.txt` / `prod.txt` — the three pip files
  (`dev.txt`/`prod.txt` each start with `-r base.txt`).
- `docker/django/Dockerfile.dev` / `Dockerfile.prod` — `COPY requirements/*.txt`
  from the project root (not from inside `app/`, since `app/` doesn't exist
  yet at this point).
- `docker/django/settings.overwrite.py` — the Postgres+Redis `settings.py`
  this project actually runs on. It's a real, version-controlled, diffable
  Python file — not something buried inline in this doc. Step 3 below just
  copies it into the generated project.
- `docker/nginx/` / `docker/caddy/` — the reverse proxy that sits in front
  of gunicorn in production and serves static files directly. nginx is the
  active default in `docker-compose.prod.yml`; Caddy is a commented-out
  alternative. See "Reverse proxy: nginx vs Caddy" in Step 6.
- `docker-compose.dev.yml` / `docker-compose.prod.yml` — api + postgres + redis
  (+ nginx in prod) services, `env_file: .env.dev` / `.env.prod`.
- `.env.dev` / `.env.prod` — `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`,
  `POSTGRES_*`, `REDIS_*`.

See the current versions of these 14 files in this repo for the exact content
in use here.

`docker/django/settings.default.py` also lives in this folder, but it is
*not* one of the 10 hand-written files — Step 3 below generates it, by
saving a copy of whatever `django-admin startproject` produced before it
gets overwritten. It's kept side-by-side with `settings.overwrite.py` purely
as a diffable reference for "what did we actually change from Django's
default", regenerated fresh on every bootstrap.

## 2. The command sequence (does everything else)

Run these in order from the project root. Nothing here is typed into a file
by hand — every generated file is produced by a command.

### Step 1 — Scaffold the Django project (no local Python needed)

A throwaway `python:3.13-slim` container installs Django, runs
`startproject`, and writes straight onto the bind-mounted host folder. Docker
creates `./app` on the host automatically because it's a bind-mount target.

```bash
docker run --rm -v "$(pwd)/app:/app" -w /app python:3.13-slim \
  bash -c "pip install --quiet django && django-admin startproject config ."
```

This produces `app/manage.py` and `app/config/{__init__,settings,urls,wsgi,asgi}.py`.

### Step 2 — Fix file ownership

The container ran as root, so the generated files are root-owned on the
host. Hand them back to your user, again via a temporary container (no
`sudo` needed):

```bash
docker run --rm -v "$(pwd)/app:/app" python:3.13-slim \
  chown -R "$(id -u):$(id -g)" /app
```

### Step 3 — Snapshot the default, then point settings.py at Postgres + Redis

`startproject` generates a sqlite/no-cache `settings.py`. First save that
generated default alongside the override, for reference/diffing:

```bash
cp app/config/settings.py docker/django/settings.default.py
```

Then overwrite the real one with the tracked override — a straight file
copy, no heredoc, no content living only inside this doc:

```bash
cp docker/django/settings.overwrite.py app/config/settings.py
```

If you ever need to change DB/cache settings, edit
`docker/django/settings.overwrite.py` (it's a real, linted, git-diffable
file) and re-run the second `cp` — don't hand-edit the generated copy under
`app/`, it'll just get overwritten next time you bootstrap. Re-run the first
`cp` too whenever you bump the Django version, so `settings.default.py`
stays an accurate snapshot of what a fresh `startproject` looks like.

### Step 4 — Build and start the dev stack

```bash
docker compose -f docker-compose.dev.yml up --build -d
```

### Step 5 — Migrate and create a superuser

```bash
docker compose -f docker-compose.dev.yml exec api python manage.py migrate
docker compose -f docker-compose.dev.yml exec api python manage.py createsuperuser
```

App: http://localhost:8008/ — Admin: http://localhost:8008/admin

### Step 6 — Production

Same `app/` is reused; only the compose file and Dockerfile differ.

#### Preparation

`.env.prod` as checked in has placeholder values
(`CHANGE-ME-run-openssl-rand--base64-50` and `...-32`) — unmistakably fake,
so nobody mistakes them for real secrets, but they still have to be
replaced before a real deploy. Generate real values and write them
straight into `.env.prod` — no copy-pasting by hand:

```bash
SECRET_KEY=$(openssl rand -base64 50 | tr -d '\n')
POSTGRES_PASSWORD=$(openssl rand -base64 32 | tr -d '\n')

sed -i "s|^SECRET_KEY=.*|SECRET_KEY=${SECRET_KEY}|" .env.prod
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=${POSTGRES_PASSWORD}|" .env.prod
```

Two things making this safe: `tr -d '\n'` strips the newline `openssl rand
-base64` inserts every 64 characters (without it, the value would spill
onto a second line and break the `.env` file); and `sed`'s delimiter here
is `|`, not the usual `/`, since generated values routinely contain `/`
themselves — using `/` as the delimiter would break the substitution on
some fraction of runs. Base64 output never contains `|`, `&`, or `\`, so no
escaping is needed either way.

Also set `ALLOWED_HOSTS` in `.env.prod` to your real domain(s), comma
separated, no scheme (`example.com,www.example.com`) — but keep `localhost`
and `127.0.0.1` in the list too; the container healthchecks below depend on
them (see the comment above `ALLOWED_HOSTS` in `.env.prod`). Treat the
committed `.env.prod` as a template, not as the file you actually deploy
with — on the real server, regenerate the secrets rather than reusing
what's in git.

Static files and the reverse proxy are already handled — see "Reverse
proxy: nginx vs Caddy" below. Known gaps still not fixed here:
- **TLS certificates**: the proxy is in place, but no real certificate is
  mounted/obtained yet. nginx needs one supplied (certbot, your provider,
  etc.); Caddy obtains and renews one on its own once a real domain is
  set — see the comments in `docker/nginx/nginx.conf` /
  `docker/caddy/Caddyfile`.
- **settings.py hardening**: see "settings.py — out of scope here" in
  `docs/guide/overview.txt` for the `SECURE_*` settings a real deployment
  needs (`SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, HSTS, etc.).

#### Reverse proxy: nginx vs Caddy

`docker-compose.prod.yml` puts a proxy in front of gunicorn that (a) serves
`/static/` directly from `static_volume`, so Python is never involved in
serving a CSS/JS/image file, and (b) is the only service that publishes a
port to the host — `api`, `postgres`, and `redis` no longer do.

**Default: nginx** (`docker/nginx/`). Chosen as the default because it's
the more widely known, more configurable option — most developers already
know its config syntax, and it behaves identically across every hosting
environment. It does *not* obtain TLS certificates on its own.

**Alternative: Caddy** (`docker/caddy/`), commented out in
`docker-compose.prod.yml`. Simpler config (`Caddyfile` vs `nginx.conf`),
and it obtains + auto-renews Let's Encrypt certificates by itself once a
real domain is pointed at it — no certbot, no manual renewal cron. It's
plenty powerful for this stack; it's the non-default only because it's
less ubiquitous than nginx.

To switch: comment out the `nginx:` service in `docker-compose.prod.yml`,
uncomment the `caddy:` block right below it (and the matching `caddy_data`
/ `caddy_config` volumes at the bottom of the file), then rebuild:

```bash
docker compose -f docker-compose.prod.yml up --build -d
```

#### Installation

```bash
docker compose -f docker-compose.prod.yml up --build -d
```

`docker-compose.prod.yml` already runs `migrate`, `collectstatic`, and
`gunicorn` as its container command — no separate exec step needed. First
boot waits on postgres/redis `healthcheck:` (`condition: service_healthy`)
before starting `api`, and waits on `api` being healthy before starting
`nginx` — so there's no manual "wait for the DB"/"wait for the app" step
either.

Create the first admin user (one-time, same command as dev):

```bash
docker compose -f docker-compose.prod.yml exec api python manage.py createsuperuser
```

#### Checking

```bash
docker compose -f docker-compose.prod.yml ps                      # all 4 services "healthy"?
docker compose -f docker-compose.prod.yml logs -f api nginx        # gunicorn + nginx access/error logs
docker inspect --format '{{json .State.Health}}' django_api_prod         # api HEALTHCHECK detail
docker inspect --format '{{json .State.Health}}' django_api_nginx_prod  # nginx HEALTHCHECK detail
docker compose -f docker-compose.prod.yml exec api python manage.py showmigrations  # confirm migrate applied everything
curl -I http://localhost/admin/login/           # through nginx -> gunicorn, should be 200
curl -I http://localhost/static/admin/css/base.css  # served by nginx directly, should be 200
```

`postgres`, `redis`, and `api` have no `ports:` in `docker-compose.prod.yml`
— on purpose, so they're reachable only from other containers on the
compose network, never from the host or the internet. `nginx` (or `caddy`)
is the sole entry point. Reach postgres/redis the same way the dev examples
in `docs/guide/database_usage.txt` and `docs/guide/redis_usage.txt` do, via
`docker compose exec`, just with `-f docker-compose.prod.yml`.

## Recap

| You write by hand | Generated by command |
|---|---|
| docker/django/Dockerfile.dev / Dockerfile.prod | app/manage.py |
| docker/django/settings.overwrite.py | app/config/__init__.py, urls.py, wsgi.py, asgi.py |
| docker/nginx/Dockerfile.prod, nginx.conf | app/config/settings.py (scaffolded, snapshotted to docker/django/settings.default.py, then overwritten by `cp` from settings.overwrite.py) |
| docker/caddy/Dockerfile.prod, Caddyfile | docker/django/settings.default.py (reference snapshot, not hand-written) |
| docker-compose.dev.yml / .prod.yml | |
| .env.dev / .env.prod | |
| requirements/base.txt, dev.txt, prod.txt | |

Zero manual `mkdir`, zero manual file creation under `app/`, zero local
Python install. Everything past the 14 template files is a copy-pasteable
command.
